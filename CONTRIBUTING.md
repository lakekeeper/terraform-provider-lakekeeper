# Contributing

Thanks for helping improve the Terraform provider for Lakekeeper. This guide covers everything from setting up your machine to getting a pull request merged.

## Getting help

For questions, ideas, or help with a contribution, join the [Lakekeeper Discord](https://discord.gg/jkAGG8p93B).

## Reporting issues

Report bugs and feature requests on the [issue tracker](https://github.com/lakekeeper/terraform-provider-lakekeeper/issues). For bugs, include the provider and Lakekeeper versions, a minimal Terraform configuration, and the expected and actual behaviour.

If you plan to fix something yourself, you can open a pull request directly with a description of the problem. For larger changes, open an issue first so we can agree on the approach. To pick up an existing issue, leave a comment and we'll assign it to you.

## Getting started

Prerequisites:

- [Go](https://go.dev/dl/), at the version in `go.mod`
- [Docker](https://docs.docker.com/get-docker/) with Compose, for the local Lakekeeper stack used by acceptance tests

Terraform does not need to be installed: `make` builds the version it needs into `bin/` on first use (this takes a few minutes once).

```sh
make build         # Build the provider into bin/
make testacc-up    # Start Lakekeeper, Keycloak, PostgreSQL and OpenFGA via Docker Compose
```

The `playground/` directory holds a sample configuration you can apply against the local stack with `make playground`; see the [README](README.md#playground).

## Making changes

### Tests

Unit tests need nothing beyond Go:

```sh
make test                          # All unit tests
RUN=TestName make test             # A single test
```

Most tests are **acceptance tests**: they carry the `//go:build acceptance` tag and create real resources in the local Lakekeeper stack. Any change to resource or data source behaviour needs one.

```sh
make testacc-up                    # Start the stack (once)
make testacc                       # All acceptance tests
RUN=TestAccName make testacc       # A single acceptance test
make testacc-down                  # Tear down the stack, removing its volumes
```

New acceptance test files start with `//go:build acceptance`; pure unit tests stay untagged so `make test` picks them up.

### Documentation

The provider docs in `docs/` are generated by [`tfplugindocs`](https://github.com/hashicorp/terraform-plugin-docs). Edit the sources instead, then run `make generate`:

- schema descriptions in the Go code
- templates in `templates/`
- examples in `examples/` (each resource has a `resource.tf` and, if importable, an `import.sh`)

CI fails when `docs/` is out of date.

### Code style

Formatting and linting are enforced by `gofmt`, [`golangci-lint`](https://golangci-lint.run/), `terraform fmt`, and `shfmt`. `make fmt` applies all of them; `make lint` checks without changing files. Keep changes consistent with the surrounding code.

GitHub Actions workflows in `.github/workflows/` are checked with [`actionlint`](https://github.com/rhysd/actionlint) and [`zizmor`](https://docs.zizmor.sh/). Run `make lint-actions` after changing them; it needs [`uv`](https://docs.astral.sh/uv/) for zizmor. CI also runs zizmor's online audits (e.g. known-vulnerable actions); set `GH_TOKEN` to run them locally too.

## Commits and branches

- Commits and pull request titles follow [Conventional Commits](https://www.conventionalcommits.org/), e.g. `fix: handle empty role list` or `feat(warehouse): support GCS`. CI checks the PR title, and [release-please](https://github.com/googleapis/release-please) derives versions and `CHANGELOG.md` from it.
- Mark a breaking change with `!` (e.g. `feat!: rename warehouse attribute`) and describe the migration in the PR.
- Name branches `type/short-description` using the commit type, e.g. `fix/role-list-pagination`.
- `CHANGELOG.md` and `.release-please-manifest.json` are maintained by release-please; leave them untouched.

## Submitting a pull request

1. Run `make reviewable` (build, format, regenerate docs, unit tests) and commit any changes it produces.
2. Run the acceptance tests for the resources you touched.
3. Open the pull request against `main` and fill in the template.
4. A maintainer from [MAINTAINERS.md](MAINTAINERS.md) reviews it; once CI is green and it is approved, it is merged.
